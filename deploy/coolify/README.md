# Scoutfile on Coolify

Scoutfile is retired in favour of VolunHub. This stack exists so the production version
(`master`) can be stopped and started again from Coolify after the EC2 host
(`scoutfile.albascout.ro`, 54.78.25.115) is shut down. It is not developed further.

## What runs where

| piece | where |
|---|---|
| code | `master`, built by Coolify from `Dockerfile` (Python 3.10, the EC2 host's interpreter) |
| stack | `docker-compose.coolify.yml`: `scoutfile-web` (gunicorn), `scoutfile-worker` (Celery, the Slack bot queue), `scoutfile-migrate` (one-shot), `scoutfile-db` (PostGIS 14), `scoutfile-redis`, `scoutfile-memcached` |
| database | inside the stack, volume `scoutfile-db-data`. Stopping the application stops it too and frees its memory; the volume keeps the data |
| static and media | unchanged: S3 + CloudFront, configured by the production `local_settings.py` |
| settings | `scoutfile3.settings_docker` = `settings` + the production `local_settings.py` (from `SCOUTFILE_LOCAL_SETTINGS_B64`) + container overrides (database, cache and broker hosts, stdout logging, Traefik) |
| JWT key | `keys/scoutfile-2023.pem` from `SCOUTFILE_JWT_KEY_B64`. Organizer accepts tokens Scoutfile signs with it |

`scoutfile-migrate` skips on a database with no `django_migrations` table, so the first deploy
never creates an empty schema for the dump to collide with. On a restored database it runs
`migrate`, which applies nothing (the July 2026 dump already has every migration of `master`).

## Moving off the EC2 host

### 1. Collect the two secrets from the EC2 host

```bash
ssh ubuntu@scoutfile.albascout.ro
base64 -w0 /var/app/scoutfile-prod/web/scoutfile3/local_settings.py; echo   # → SCOUTFILE_LOCAL_SETTINGS_B64
base64 -w0 /var/app/scoutfile-prod/keys/scoutfile-2023.pem; echo            # → SCOUTFILE_JWT_KEY_B64
grep -A3 "'NAME'" /var/app/scoutfile-prod/web/scoutfile3/local_settings.py  # database name for step 3
```

### 2. Create the application

Coolify → project (new: `scoutfile`) → *+ New → Public Repository* →
`https://github.com/andreiavram/scoutfile`:

| field | value |
|---|---|
| branch | `master` |
| build pack | Docker Compose |
| compose file | `/docker-compose.coolify.yml` |
| auto-deploy | off |

Environment: `SCOUTFILE_LOCAL_SETTINGS_B64`, `SCOUTFILE_JWT_KEY_B64` from step 1, and
`DJANGO_ALLOWED_HOSTS=scoutfile.albascout.ro,centru.albascout.ro,knowledge.albascout.ro,<test host>`
while you test on a temporary hostname. `SERVICE_PASSWORD_POSTGRES` and
`SERVICE_BASE64_64_DJANGOSECRET` are generated by Coolify.

Domain on **`scoutfile-web` only**: the temporary hostname for now, e.g.
`https://scoutfile-test.yetilabs.ro:8000` (any hostname works: `django_hosts` sends an unknown one
to the main site). Do not add the `albascout.ro` names before their DNS points here: Traefik tries
the certificate once and never retries.

Deploy. `scoutfile-migrate` prints `the database has no django_migrations table` and the web
healthcheck fails until the dump is restored. That is expected.

### 3. Freeze the old production and restore its data

```bash
# EC2 host: stop writes, then dump
sudo supervisorctl status
sudo supervisorctl stop scoutfile-prod            # and any Celery program listed for prod
sudo -u postgres pg_dump -Fc -d <database name from step 1> -f /tmp/scoutfile-final.dump

# this machine → Coolify host
scp ubuntu@scoutfile.albascout.ro:/tmp/scoutfile-final.dump .
scp scoutfile-final.dump <coolify host>:~

# Coolify host
DB=$(docker ps -qf name=scoutfile-db- | head -1)
docker cp ~/scoutfile-final.dump "$DB":/tmp/scoutfile.dump
docker exec "$DB" pg_restore -U scoutfile -d scoutfile --no-owner --no-privileges /tmp/scoutfile.dump
docker exec "$DB" psql -U scoutfile -d scoutfile -Atc "select count(*) from auth_user; select count(*) from structuri_membru; select max(last_login) from auth_user"
```

The restore was rehearsed with the July 2026 dump into a database with the extensions the
`postgis/postgis` image pre-creates: no errors, 627 users, 604 members. Expect at least those
numbers.

Redeploy. `scoutfile-migrate` now runs `migrate` (nothing to apply) and `scoutfile-web` becomes
healthy.

### 4. Check it on the temporary hostname

Log in; open a member, an event album (images come from CloudFront) and the documents list.

### 5. Move the hostnames

1. Point the A records of `scoutfile.albascout.ro`, `centru.albascout.ro` and
   `knowledge.albascout.ro` at the Coolify host.
2. Once `dig +short scoutfile.albascout.ro` answers the Coolify host, set the domains of
   `scoutfile-web` to
   `https://scoutfile.albascout.ro:8000,https://centru.albascout.ro:8000,https://knowledge.albascout.ro:8000`,
   drop the temporary hostname (also from `DJANGO_ALLOWED_HOSTS`) and redeploy.
3. Check https://scoutfile.albascout.ro/login/ and a JWT login from Organizer.

### 6. Retire the EC2 host

1. Disable the staging workflow, which deploys over SSH to the same host:
   `gh workflow disable deploy-to-staging -R andreiavram/scoutfile`.
2. Keep `scoutfile-final.dump` somewhere durable (S3) — the cold copy if the volume is ever lost.
3. Stop the EC2 instance; terminate it (and its EBS volume) once you are sure. The S3 bucket and
   the CloudFront distribution stay: static and media are served from them.

## Turning it off and on

Coolify → the application → *Stop*. Every container stops, `scoutfile-db-data` stays. *Start*
(or *Redeploy*) brings it back with the data as it was.
